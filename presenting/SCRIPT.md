## พรหมพัฒน นาทีที่ 8 ถึง 12 หน้า 8 ถึง 10 สลับกับสาธิต

หน้า 8 พูดว่า p50 41.2 มิลลิวินาที และ p95 68.1 มิลลิวินาที วัดในคอนเทนเนอร์บนเครื่องของกลุ่ม จากนั้นยิงสามคำขอทันที

1. `GET /health` ต้องเห็น hist_gb เวอร์ชัน 2
2. `POST /predict` ด้วย `examples/predict.json`
3. `POST /predict` ฝนเท่ากับ -5 ต้องเห็นสถานะ 422 และ `rejected_by_schema_gate`

หน้า 9 ประโยคที่ต้องพูด: ในกรณีจำลอง อินพุตเลื่อนคือ data drift drift share 0.524 เกิน 0.30 จึงสั่งฝึกใหม่ ส่วน recall 0.998 ไม่ใช่ตัวสั่ง ส่วน concept drift คือป้ายเปลี่ยนทั้งที่อินพุตไม่เลื่อน drift share 0.000 แต่ recall 0.380 และ 0.389 ต่ำกว่า 0.60 สองหน้าต่างติดกัน สองหน้าต่างติดกันผูกกับ recall ไม่ได้ผูกกับ drift share

จากนั้นเปิด `reports/rollback.json` ให้ดูว่า alias ย้ายจากเวอร์ชัน 4 กลับเวอร์ชัน 2 แล้ว ห้ามรันสคริปต์ย้อนเวอร์ชันสด

หน้า 10 เปิด Pull Request ที่ลดขอบฝนจาก 0 เป็น -10 เป็นตัวหลัก งานข้อมูลและงานโมเดลไม่ผ่านเพราะเทสต์คาดว่าค่า -5 ต้องถูกปฏิเสธ ห้ามกด merge ถ้าเปิด GitHub ไม่ได้ ให้ใช้ `reports/ci_fail.txt` ปิดด้วยประโยคว่าผู้อื่นรันจากเครื่องเปล่าตาม README ได้ และ CI บน GitHub Actions คือสามงานตรวจ การขึ้นให้บริการทำผ่าน blessing แล้วเสิร์ฟด้วย FastAPI ไม่ได้ deploy อัตโนมัติจาก Actions

## คำถามที่ควรตอบได้

- ถ้าโมเดลผิด ใครเดือดร้อน: เกษตรกรที่พ่นสารหรือเก็บเกี่ยวผิดจังหวะ
- ธุรกิจกับโมเดลเชื่อมกันอย่างไร: ต้นทุน 5 และ 1 ใช้เลือก threshold บนชุด validation และกลายเป็นต้นทุนในตารางหน้า 5
- drift สองแบบต่างกันอย่างไร: กรณีจำลอง อินพุตเลื่อนคือ data drift ป้ายเปลี่ยนทั้งที่อินพุตนิ่งคือ concept drift
- ระบบต้องเร็วแค่ไหน: p95 ไม่เกิน 150 มิลลิวินาที วัดในคอนเทนเนอร์ได้ 68.1 มิลลิวินาที
- โมเดลใหม่แย่แล้วรู้อย่างไร: blessing กันก่อนขึ้นให้บริการ หลังขึ้นแล้วการเฝ้าระวังเป็นคนละเรื่อง ถ้า drift share ถึง 0.30 หรือ recall ต่ำกว่า 0.60 สองหน้าต่างติดกัน จะสั่งฝึกใหม่ การย้าย alias กลับไม่เกิดอัตโนมัติ รอบนี้ย้ายจากเวอร์ชัน 4 กลับเวอร์ชัน 2 เพื่อโชว์ว่าทำได้
